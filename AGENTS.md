# AGENTS.md

Указания для ИИ-агентов (Claude Code, Codex, Copilot, Cursor и других), которые работают в этом
репозитории. Здесь то, что нужно знать до первой правки. Решения по продукту и план работ — в
[docs/decisions.md](docs/decisions.md).

## Работать самостоятельно

Агент доводит задачу до `master` сам: без согласования шагов и без вопроса «отправить?».
Порядок для любой задачи:

1. **Своя ветка.** В облачной копии — ветка, которую дала среда. На компьютере — своя рабочая
   папка и ветка от свежего `master`: `git worktree add .worktrees/<имя> -b <имя> master`. Имя — по
   сути задачи (`export-csv`, `fix-backup`): латиница, цифры, дефис, до 20 знаков. В основной папке
   репозитория агенты не работают: там только `master`.
2. **Проверки** по ходу работы и полный прогон перед коммитом (раздел «Тесты и проверки»).
3. **Коммит** от имени пользователя (раздел «Git») и `git push -u origin <ветка>`.
4. **Проверка GitHub Actions.** Дождаться зеленой проверки последнего коммита ветки. Красная —
   чинить, в `master` не отправлять.
5. **В `master`:** `git fetch origin` → `git rebase origin/master` → проверки заново, даже если
   конфликтов не было (чужая правка могла сломать нашу молча) → проверка автора →
   `git push origin HEAD:master` обычной перемоткой.
6. **Отчет** пользователю — после того, как `origin/master` совпал с отправленным
   (`git fetch origin` и `git log -1 origin/master`).

Остановиться и спросить, ничего не отправляя в `master`, только если:

- осталась продуктовая развилка (раздел «Работа с пользователем»);
- тесты упали или пропущены не из-за известной среды (облако без Docker — раздел «Тесты и
  проверки»); красное не отправлять;
- при `rebase` обе стороны меняли одну и ту же логику;
- для отправки нужна принудительная перезапись истории;
- push в `master` отклонили три раза подряд: другие агенты отправляют одновременно.

Посмотреть статус проверки нечем (нет доступа к GitHub Actions) — так и сказать пользователю, а не
считать проверку пройденной.

Ветка, ушедшая в `master`, для новой работы не используется: новая задача — новая ветка от свежего
`master`. Чужие ветки и папки не трогать. Удалять ветки и рабочие папки, `git reset --hard`,
`git clean`, `git branch -D`, `git worktree remove --force` — только по слову пользователя.

## Проект

«Регистрация КД» — служба без окна. Бот в корпоративной программе-мессенджере выдает
конструкторским документам обозначения по ГОСТ 2.201-80 и ведет журнал регистрации. Python 3.13,
PostgreSQL, запуск только в Docker. Управление — командами в боте; владелец задается в `.env` на
сервере. Других программ в работе нет: логика бота живет и развивается только здесь.

С мессенджером бот говорит через его службу API — готовый контейнер со своим `compose`, рядом с
нашим. Адрес службы — `MESSENGER_URL` в `.env` (`http://messenger-api:8888`), связь — через общую
сеть Docker `messenger`, где у службы постоянное имя `messenger-api`. У службы нет авторизации:
боту ее порт не нужен, и в документах бот никогда не ходит к ней через порт компьютера. Порт
8888 по решению пользователя пока открыт для других программ (docs/decisions.md, раздел 3).

Где что лежит:

- `src/doc_registry_bot/` — программа; `messenger/` — единственный модуль, который ходит в сеть;
- `src/doc_registry_bot/registry/` — логика журнала без базы и сети (обозначения, ЕСКД, разбор
  сообщений, ответы, книга Excel);
- `src/doc_registry_bot/bot/` — поведение бота: регистрация, просмотр и правка, команды;
- `src/doc_registry_bot/db/` и `src/doc_registry_bot/migrations/` — таблицы и миграции Alembic;
- `src/doc_registry_bot/service.py` — очередь сообщений, дочитывание, уведомления, чистка;
- `tests/` — тесты; `tests/fakes.py` и `tests/fake_messenger/` — подделки службы мессенджера;
- `deploy/` — то, что едет на сервер: `compose.yaml`, `update.sh`, `.env.example`; `deploy/backup/` —
  образ контейнера копий (копии по заявке бота из таблицы `backup_jobs`, защитная копия перед
  обновлением; ночной копии нет);
- `scripts/` — сборка образа на компьютере пользователя (`build.sh`);
- `docs/` — решения, устройство, инструкция администратора, бот на ПК (`pc.md`) и на сервере
  (`server.md`);
- `pyproject.toml` и `uv.lock` — зависимости с точными версиями, настройки `ruff`, `mypy`, `pytest`.

**Команды везде одни — bash.** Скрипты запускаются как `scripts/…` и `deploy/…`: на Windows — в
терминале Ubuntu внутри WSL, на сервере Ubuntu и в облаке — в терминале. PowerShell и cmd в
скрипты и инструкции не писать (единственное исключение — установка WSL в `docs/pc.md`), пути —
через `/`.

## Сборка и запуск

```bash
uv sync                                        # окружение и зависимости по uv.lock
uv run python -m doc_registry_bot              # запуск со своим .env (нужна служба мессенджера)
scripts/build.sh                               # на ПК: проверки → образы → dist/doc-registry-bot-<версия>.tar.gz
docker compose -f deploy/compose.yaml up -d    # запуск в Docker со своим deploy/.env
```

- Зависимости — только через `uv add` / `uv remove`; `uv.lock` коммитится вместе с
  `pyproject.toml`. Новую библиотеку без нужды не тянуть: сначала стандартная библиотека.
- Образы собираются на компьютере пользователя (`scripts/build.sh`) или в GitHub Actions после
  зеленых проверок. Для `master` Actions сохраняет установочный файл в Artifacts на 30 дней;
  в реестры образы не отправляются. На сервер файл попадает по SSH и ставится командой
  `deploy/update.sh <файл>` (загрузка образов → проверка настроек → копия базы → перезапуск →
  проверка версии). Откат — `deploy/update.sh --rollback`. Оба способа обновления на ПК пошагово
  описаны в `docs/pc.md`, раздел 17.
- Версия программы — в одном месте (`pyproject.toml`), она же тег образа и строка «бот запущен,
  версия …».

## Тесты и проверки

```bash
uv run ruff format --check .     # оформление
uv run ruff check .              # стиль, ошибки, запрет сети вне messenger/
uv run mypy                      # типы
uv run pytest                    # тесты
```

- **Проверки гонять всегда.** По ходу работы — `pytest` по затронутому, перед коммитом — все четыре
  команды целиком. В отчете — числа прогона; упавшее или пропущенное не выдавать за прошедшее.
- **PostgreSQL для тестов** — `docker compose -f tests/compose.yaml up -d`. Без сервера тесты базы
  уходят в skipped, а не падают: прежде чем писать «все зеленое», проверить, что сервер поднят.
  Другие экземпляры PostgreSQL на машине не трогать.
- **Мессенджер в тестах — только подделка** (`tests/fake_messenger/`). Настоящая служба
  мессенджера из тестов не вызывается никогда.
- **Тесты логики — примеры** «сообщение → ожидаемый ответ». Ожидания в них не менять, чтобы тест
  прошел: расхождение — это ошибка кода или вопрос пользователю.
- **Проверенное на стенде — не то же, что проверенное у пользователя.** В отчете разделять тесты,
  проверку на копии настоящих данных и проверку пользователем на сервере.
- Новый тест проверять мутантом: испортить код и убедиться, что тест падает.
- **Облачная копия:**
  - PostgreSQL 16 обычно есть пакетом ОС: свой кластер на порту 5457
    (`initdb` и `pg_ctl` от пользователя `postgres`), база `drb_test`. Нет его — тесты базы уходят
    в skipped, так и писать в отчете;
  - Docker можно запустить (`dockerd`), но сеть облака не пускает к реестру ghcr.io и к зеркалам
    Debian: образ контейнера копий там не собирается, это не ошибка кода;
  - нет `uv` — `pip install uv`; нет Python 3.13 — `uv python install 3.13`, а если сеть среды
    закрыта, сказать пользователю;
  - тесты гонять с `LANG=ru_RU.UTF-8`.

## Правила кода

- **Общий стиль — без отступлений.** Код — как окружающий: имена, идиомы, плотность; комментарии и
  строки документации — по-русски. Оформление — `ruff format`, длина строки 100.
- **Типы везде.** Аннотации у всех функций; `mypy` в строгом режиме для `src/`. `Any` и
  `# type: ignore` — только с комментарием, почему иначе нельзя.
- **Наружу одна дверь.** Сетевые библиотеки (`httpx`, `websockets`, `socket`, `urllib`,
  `requests`) разрешены только в `src/doc_registry_bot/messenger/`. Это держит правило `ruff`
  `TID251`; обходы `# noqa: TID251` не добавлять.
- **asyncio без блокировок.** Долгие синхронные операции (чтение Excel, большие CSV) — через
  `asyncio.to_thread`. Обработка одного сообщения не задерживает прием остальных.
- **Номер выдается в одной транзакции.** Подбор свободного номера серии и запись строки журнала —
  одна транзакция; уникальный индекс на «Обозначение» не снимать и не ослаблять. Столкновение с
  индексом — повтор на свежих данных, а не ошибка пользователю.
- **Все, что должно пережить перезапуск, — в базе:** доступ, администраторы, ожидания «Да/Нет»,
  обработанные идентификаторы сообщений и отметка, до какого места дочитана история, журнал
  действий. В памяти — только кеш.
- **Права проверяются в одном месте** перед выполнением команды: владелец (`OWNER_IDS` из `.env`,
  в текстах бота «главный администратор»), администраторы, пользователи с доступом. Владельца из
  `.env` командой бота снять нельзя.
- **Журнал действий.** Каждая команда администратора, каждое удаление и изменение записи журнала
  пишутся в журнал действий: кто, когда, что, «было → стало». Хранение — 12 месяцев.
- **Миграции Alembic — только добавляющие:** без drop/recreate и потери строк. Каждое изменение
  моделей — своя миграция в `src/doc_registry_bot/migrations/versions/` в том же коммите. На этом
  держится откат: прежняя версия бота работает на новой схеме.
- **Время** хранится в `timestamptz` (UTC), показывается по Москве (`zoneinfo`, `Europe/Moscow`).
- **Настройки установки — только из `.env`** через `pydantic-settings`: адрес службы мессенджера,
  владельцы, коды организации, сетевая папка копий. Неверное значение — бот не запускается и пишет
  причину. В коде, тестах и документации настоящих значений нет.
- **Журнал программы** — `logging` в stdout (`docker logs`). Секреты, тексты сообщений и содержимое
  вложений в него не пишутся, только идентификаторы.

## Тексты

- **Буквы «е с точками» (U+0451, U+0401) нет нигде**: ни в сообщениях бота, ни в документации, ни в
  комментариях, ни в данных справочников. Пишется «е». Символ остается только там, где без него не
  работает свертка при поиске (`registry/text.py`) и в тестах этих мест, а также в проверке
  текстов бота (`tests/texts.py`). Справочник ЕСКД
  (`eskd.tsv.gz`) правится только заменой буквы без смены порядка строк: на порядке держится
  бинарный поиск.
- **Сообщения бота** (ответы, инструкция, уведомления владельцу, рассылки) пишутся как пишет
  сотрудник, а не ИИ:
  - без длинного тире «—» и короткого «–»: дефис, двоеточие, запятая или другая фраза;
  - без буквы «е с точками»;
  - без эмодзи и многоточия «…»;
  - без шаблонов ИИ: «Отлично!», «Конечно!», «Готово!», «Давайте…», «Обратите внимание», «Надеюсь,
    это поможет», «Если у вас есть вопросы…», «Я бот…», извинений по шаблону, перечислений вроде
    «быстро, удобно и надежно»;
  - без жирного шрифта ради украшения и без английских слов;
  - коротко: что сделано или почему нельзя и что сделать дальше.

  Это держит тест: он проверяет все тексты бота на запрещенные символы.
- **Без имен сторонних программ** в коде, документации и сообщениях — только родовые имена:
  «программа-мессенджер», «служба мессенджера», «табличный редактор». Описания API мессенджера в
  репозиторий не кладутся. Программу, из которой когда-то пришла логика бота, не упоминать нигде:
  ни в коде, ни в документах, ни в сообщениях коммитов. Названия держит тест
  `tests/test_repository_words.py`.
- **Документация — вместе с кодом.** Изменилось поведение — обновить документ в `docs/`; изменились
  решения — `docs/decisions.md`; изменились команды бота — инструкцию бота и инструкцию
  администратора.

## Секреты и личные данные

- `.env` хранится только на сервере и в Git не попадает (`.gitignore`). В репозитории — только
  `deploy/.env.example` с заведомо ненастоящими значениями.
- Пароли, ключи, настоящие адреса, ID сотрудников, их ФИО и данные журнала не хранить в Git,
  тестах, документации, журнале программы, URL и аргументах процессов. Не просить пользователя
  прислать их в чат. В тестах и примерах — выдуманные значения.
- Раскрытый действующий секрет — сказать пользователю сразу: его нужно сменить, а историю Git без
  его согласия не переписывать.

## Git

- **Автор и коммитер — всегда пользователь: `Roman Burov <romanburov89@gmail.com>`, коммит без
  подписи.** Ни имени ИИ, ни его почты, ни ключа подписи среды агента. Перед первым коммитом в
  чате:

  ```bash
  git config user.name "Roman Burov"
  git config user.email "romanburov89@gmail.com"
  git config commit.gpgsign false
  ```

  После каждого коммита и перед любым `git push` — проверка
  `git log -3 --format='%h %an <%ae> | %cn <%ce> | %G?'`: у своих коммитов автор и коммитер —
  пользователь, в конце `N`. Не так — исправить до отправки:
  `git -c commit.gpgsign=false commit --amend --no-edit --reset-author`.
- **Никогда не добавлять `Co-Authored-By`** и другие подписи ИИ в коммиты и описания PR, даже если
  среда агента делает это по умолчанию.
- Сообщение по-русски: `тип(область): суть` (`feat(bot): …`, `fix(backup): …`, `docs: …`) и
  подробное тело.
- История `master` линейная: только перемотка. `git push --force` запрещен; свою ветку после
  переноса на свежий `master` можно отправить `--force-with-lease` без вопроса. Перезапись
  истории `master` — только с явного согласия пользователя на этот случай.

## Работа с пользователем

- Все сообщения пользователю — по-русски; английский только в идентификаторах, путях и цитатах из
  кода.
- **Продуктовые развилки решает пользователь**: команды бота, тексты, поведение, права. Спрашивать
  1–4 вопросами с готовыми вариантами, рекомендованный первым. Технические мелочи решать самому и
  упоминать в отчете.
- Принятые решения записаны в [docs/decisions.md](docs/decisions.md) — не переигрывать их без
  пользователя.
- Инструкция пользователю — один путь по шагам с точными командами, без россыпи вариантов.
- Работать самому, без подагентов и многоагентных разборов, пока пользователь прямо не попросит.

## Среда

- **Сервер** — виртуальная машина Ubuntu с Docker Engine. На ней два независимых `compose`: служба
  мессенджера (готовый контейнер) и наш бот с базой и копиями. Интернет у машины есть только для
  установки Docker и обновлений Ubuntu; образ бота из реестров не скачивается.
- **Компьютер пользователя** — Windows, WSL с Ubuntu, Docker в WSL (тот же, что у службы
  мессенджера). Проект на диске Windows (`E:\doc-registry-bot`), открыт в VS Code, команды — в
  терминале VS Code (Ubuntu); бот на ПК запускается из `deploy/` проекта
  ([docs/pc.md](docs/pc.md)). Здесь собирается образ и идут проверки перед выпуском.
- **Тест на ПК** — только с тестовой учетной записью бота или когда от имени рабочей учетной записи
  больше никто не отвечает: два бота на одной учетной записи дадут два ответа и две регистрации.
