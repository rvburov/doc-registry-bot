# Регистрация КД: бот на ПК (проект на диске Windows, VS Code, Docker в WSL)

Пошагово: проверка и установка, проект в VS Code, сборка, связь со службой мессенджера, `.env`,
первый запуск, журнал, пользователи, выгрузка файлов, резервные копии, остановка и обновление.
**Каждый шаг установки начинается с проверки:** что уже есть, то не ставится заново. Шаг 0
проверяет все сразу и говорит, какие шаги пропустить.

Как это устроено:

- папка проекта лежит на диске Windows: `E:\doc-registry-bot`. VS Code открывает ее как обычную
  папку, файлы видны и в Проводнике;
- команды набираются в терминале VS Code, а терминал этот — Ubuntu (WSL). Команды те же, что на
  сервере ([server.md](server.md));
- бот работает в том же Docker, что и служба мессенджера, и находит ее по общей сети Docker
  `messenger`;
- бот на ПК запускается прямо из папки проекта `deploy`: там `compose.yaml`, скрипты, `.env` и
  резервы `backups` (`.env` и резервы в Git не попадают).

| Windows | Ubuntu (терминал) | Что |
|---|---|---|
| `E:\doc-registry-bot` | `/mnt/e/doc-registry-bot` | проект: код, сборка |
| `E:\doc-registry-bot\deploy` | `/mnt/e/doc-registry-bot/deploy` | рабочая папка бота: `.env`, скрипты, резервы |
| `E:\bot-files` | `/mnt/e/bot-files` | ваши файлы: журнал, списки (можно любую папку) |
| `E:\doc-registry-bot\deploy\backups` | `/mnt/e/doc-registry-bot/deploy/backups` | резервные копии: папка 1 для копий из чата и копии `./backup.sh` |

Диски Windows видны в Ubuntu как папки: `C:` — `/mnt/c`, `E:` — `/mnt/e`. Проект на другом диске
— в командах своя буква.

## 0. Проверка: что уже установлено

**WSL (в Windows).** **Пуск** → наберите «Терминал» → откройте и выполните:

```text
wsl -l -v
```

| Что видно | Что делать |
|---|---|
| строка с `Ubuntu` (например, `Ubuntu` или `Ubuntu-24.04`), в столбце `VERSION` стоит `2` | WSL готов, шаг 1 пропустите. Запомните имя Ubuntu из этой строки |
| строка с `Ubuntu`, но `VERSION` стоит `1` | `wsl --set-version ИМЯ 2` (ИМЯ — из этой строки), потом шаг 1 пропустите |
| Ubuntu в списке нет или команда не найдена | шаг 1 |

Строки `docker-desktop` и `docker-desktop-data` — служебные Docker Desktop, это не Ubuntu.

**Все остальное (в Ubuntu).** **Пуск** → **Ubuntu** (имя из списка выше). Вставьте блок целиком
(вставить в окно Ubuntu: правая кнопка мыши или `Ctrl+Shift+V`):

```bash
. /etc/os-release; echo "Ubuntu: $VERSION_ID"
docker version --format 'Docker: {{.Server.Platform.Name}}'
docker compose version
git --version
uv --version
date +'Время: %Z'
docker ps --format 'Контейнер: {{.Names}}'
docker network inspect messenger --format 'Сеть messenger: {{range .Containers}}{{.Name}} {{end}}'
ls -d /mnt/e/doc-registry-bot
```

| Строка вывода | В порядке, если | Иначе |
|---|---|---|
| `Ubuntu: …` | `22.04` или новее | шаг 1: поставьте Ubuntu 24.04 рядом со старой |
| `Docker: …` | любое имя | `command not found`, `Cannot connect` или `permission denied` — шаг 2 |
| `Docker Compose version …` | версия `v2…` или новее | шаг 2 |
| `git version …` | есть версия | шаг 3 |
| `uv …` | есть версия | шаг 3 |
| `Время: …` | `MSK` | шаг 3, часовой пояс |
| `Контейнер: …` | среди строк есть служба мессенджера | см. ниже «Службы нет в списке» |
| `Сеть messenger: …` | есть имя службы мессенджера | шаг 6 |
| `ls: …/mnt/e/doc-registry-bot` | папка есть (`No such file` — нет) | шаг 4 |

Строки с `command not found` или `No such …` — этого нет, нужен шаг из таблицы.

**Python** боту не нужен ни в Windows, ни в Ubuntu: `uv` сам скачает Python 3.13 только для этого
проекта. Установленный Python не мешает, удалять его не надо.

**Служба мессенджера и бот должны быть в одном Docker**, иначе они не увидят друг друга. Если
служба есть в строках `Контейнер: …`, все в порядке: бот, запущенный из этого же терминала,
окажется в том же Docker. Если службы в списке нет, проверьте, что она запущена, и что вы
открыли ту же Ubuntu, из которой запускается служба. Пока служба не видна в `docker ps`,
дальше не идите.

## 1. WSL и Ubuntu (только если нет по шагу 0)

1. **Пуск** → наберите «Терминал» → правой кнопкой → **Запуск от имени администратора**.
2. Выполните:

   ```text
   wsl --install -d Ubuntu-24.04
   ```

3. Перезагрузите компьютер, если попросит.
4. **Пуск** → **Ubuntu 24.04**. При первом запуске придумайте имя пользователя Linux и пароль
   (пароль понадобится для команд с `sudo`, при вводе он не отображается).
5. Повторите проверку из шага 0 в новой Ubuntu.

## 2. Docker (только если нет по шагу 0)

Служба мессенджера уже работает в Docker, поэтому обычно Docker есть, и этот шаг не нужен. Что
показала строка `Docker:` в шаге 0:

| Что видно | Что делать |
|---|---|
| `Cannot connect to the Docker daemon` | Docker не запущен. Docker Desktop: **Пуск** → **Docker Desktop**, дождитесь **Engine running**. Docker внутри Ubuntu: `sudo service docker start`. Затем повторите шаг 0 |
| `permission denied` и `docker.sock` | `sudo usermod -aG docker $USER`, закройте окно Ubuntu и откройте снова |
| `docker: command not found`, а Docker Desktop установлен | Docker Desktop → **Settings** → **Resources → WSL integration** → включите переключатель с именем вашей Ubuntu → **Apply & restart** |
| `docker: command not found`, и Docker Desktop нет | установите Docker Desktop с docker.com (в установщике оставьте **Use WSL 2 instead of Hyper-V**), затем строка выше |
| `Docker Compose` нет или версия `v1` | обновите Docker Desktop до последней версии |

После любого исправления повторите проверку из шага 0.

## 3. Инструменты в Ubuntu (только то, чего нет по шагу 0)

Нет `git`:

```bash
sudo apt-get update
sudo apt-get install -y git curl
```

Нет `uv` (`uv` из Windows в Ubuntu не виден, нужен свой):

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
source "$HOME/.local/bin/env"
```

Время не `MSK`:

```bash
sudo timedatectl set-timezone Europe/Moscow
```

Если ответ `System has not been booted with systemd`, то так:

```bash
sudo ln -sf /usr/share/zoneinfo/Europe/Moscow /etc/localtime
```

**Окружение Python внутри Ubuntu** (один раз, даже если `uv` уже был). Проект лежит на диске
Windows, а окружение Python с библиотеками лучше держать внутри Ubuntu: так сборка в разы быстрее
и надежнее.

```bash
grep -q UV_PROJECT_ENVIRONMENT ~/.bashrc || echo 'export UV_PROJECT_ENVIRONMENT="$HOME/.venvs/doc-registry-bot"' >> ~/.bashrc
source ~/.bashrc
```

Повторите проверку из шага 0: все строки в порядке.

## 5. Файл бота

Есть два способа получить один и тот же установочный файл: собрать на своем ПК или скачать
готовый из GitHub Actions. Выполните один из вариантов ниже. Если бот уже установлен и его
нужно обновить, переходите сразу к шагу 17: там оба способа приведены вместе с установкой.

Все команды — в терминале Ubuntu/WSL в VS Code. В примерах проект находится в
`E:\doc-registry-bot`; если у вас другая папка, замените ее путь в командах и в Проводнике.
В примерах версия `1.3.0`; для другой версии используйте число из имени установочного файла.
При ошибке команды остановитесь и разберите ее по шагу 18.

### Вариант 1. Собрать на своем ПК

Для сборки нужны Git, uv и работающий Docker (шаги 0–3), интернет для загрузки Python,
библиотек и базовых образов Docker.

1. Получите код и скрипты из `master`:

   ```bash
   cd /mnt/e/doc-registry-bot
   git switch master
   git pull --ff-only origin master
   ```

2. Запустите отдельную базу для тестов и проверьте ее готовность:

   ```bash
   docker compose -f tests/compose.yaml up -d
   docker compose -f tests/compose.yaml exec -T postgres pg_isready -U postgres -d drb_test
   ```

   Вторая команда должна вывести `accepting connections`. Если база еще запускается,
   повторите вторую команду через несколько секунд.

3. Запустите проверки и сборку:

   ```bash
   scripts/build.sh
   ```

   Скрипт проверит оформление, стиль, типы и тесты, соберет образы бота и контейнера копий,
   сохранит их вместе с PostgreSQL в один архив. В итогах тестов не должно быть `failed` или
   `skipped`: при пропусках проверьте тестовую базу и повторите сборку.

4. Дождитесь строки `Собрано: dist/doc-registry-bot-1.3.0.tar.gz`. Проверьте файл:

   ```bash
   ls -lh dist/doc-registry-bot-1.3.0.tar.gz
   ```

   Это готовый файл для установки. Скачивать Artifacts при этом способе не требуется.

### Вариант 2. Скачать готовую сборку из GitHub Actions

1. Получите код и скрипты из `master`:

   ```bash
   cd /mnt/e/doc-registry-bot
   git switch master
   git pull --ff-only origin master
   ```

2. В браузере откройте https://github.com/rvburov/doc-registry-bot/actions и войдите в GitHub.
   Откройте последний запуск «Проверки» ветки `master`. Дождитесь зеленой галочки, если он еще
   выполняется: установочный файл появляется только после успешных проверок и сборки.
3. Внизу страницы, в разделе **Artifacts**, нажмите `doc-registry-bot-<версия>`. Скачается ZIP
   около 200 МБ; версия должна совпадать с `version` в полученном `pyproject.toml`.
4. Распакуйте только скачанный ZIP в Проводнике: «Извлечь все» → папка
   `E:\doc-registry-bot\dist`. Создайте ее, если нет. Внутри будут
   `doc-registry-bot-<версия>.tar.gz`, `compose.yaml`, скрипты и `.env.example`.
   Файл `.tar.gz` должен лежать прямо в `dist`, без дополнительной вложенной папки.
   Сам `.tar.gz` не распаковывайте.
5. Проверьте файл в терминале:

   ```bash
   ls -lh /mnt/e/doc-registry-bot/dist/doc-registry-bot-1.3.0.tar.gz
   ```

   При этом способе `scripts/build.sh` запускать не нужно. Artifacts хранятся на GitHub
   30 дней; если нужный файл истек, используйте сборку на своем ПК.

После выбранного варианта продолжайте с шага 6. Для установки на сервер используется тот же
архив и файлы из `dist`: [server.md](server.md), шаг 6.

## 6. Связь со службой мессенджера (один раз)

Бот и служба мессенджера — два отдельных контейнера. Чтобы бот нашел службу, нужна общая сеть
Docker `messenger`, а в ней у службы постоянное имя `messenger-api`. Делается это **до первого
запуска бота**: без сети бот не запустится, без службы в сети он ее не найдет.

Проверка (то же, что строка `Сеть messenger:` в шаге 0):

```bash
docker network inspect messenger --format '{{range .Containers}}{{.Name}} {{end}}'
```

| Что видно | Что делать |
|---|---|
| имя службы мессенджера | связь уже есть, шаг пропустите |
| `Error: No such network` | все команды ниже |
| пусто или имени службы нет | команды ниже, кроме первой |

**Узнайте имя контейнера мессенджера:**

```bash
docker ps --format '{{.Names}}'
```

В списке найдите контейнер службы мессенджера (не `doc-registry-bot-...` и не `tests-...`),
например `pl-bot-794639`. Во всех командах ниже вместо `ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА` подставьте
это имя.

**Выполните по очереди:**

```bash
docker network create messenger
docker network connect --alias messenger-api messenger ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА
docker network inspect messenger --format '{{range .Containers}}{{.Name}} {{end}}'
```

Что делает каждая команда и что должно появиться:

1. `docker network create messenger` — создает общую сеть Docker с именем `messenger`, через нее
   бот и мессенджер будут видеть друг друга. В ответ появится длинная строка из букв и цифр (номер
   сети): так и должно быть. Ответ `already exists` — сеть уже есть, это тоже нормально.
2. `docker network connect ...` — включает контейнер мессенджера в эту сеть и дает ему
   постоянное имя `messenger-api`: по нему бот найдет мессенджер (строка `MESSENGER_URL` в шаге
   7). Если все в порядке, команда ничего не выводит.
3. `docker network inspect ...` — проверка: выводит, кто подключен к сети. В ответе должно быть
   имя контейнера мессенджера.

Служба при этом не останавливается, ее настройки и порт не меняются. Бот подключится к сети сам
при запуске: это прописано в его `compose.yaml`.

Порт службы внутри Docker:

```bash
docker port ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА
```

Строка вида `8888/tcp -> 0.0.0.0:8888`: число слева — порт для `.env` (шаг 7), обычно `8888`.

Если контейнер службы когда-нибудь пересоздадут (обновят или удалят и запустят заново), повторите
вторую команду: подключение к сети при этом пропадает. При перезапуске ПК, Docker или бота
повторять ничего не нужно.

## 7. Настройки `.env`

```bash
cd /mnt/e/doc-registry-bot/deploy
cp -n .env.example .env
openssl rand -hex 24
```

- `cp -n` создает `.env` из образца, а если `.env` уже есть, не трогает его;
- `openssl rand -hex 24` выводит готовый пароль для базы: выделите строку мышью и скопируйте.

Откройте `deploy\.env` в VS Code (слева в списке файлов) и заполните:

| Строка | Что вписать | Откуда взять |
|---|---|---|
| `BOT_VERSION` | версию, например `1.3.0` | имя файла `dist/doc-registry-bot-1.3.0.tar.gz` из шага 5 |
| `MESSENGER_URL` | `http://messenger-api:8888` | имя из шага 6; если порт в шаге 6 не `8888` — свой порт |
| `MESSENGER_NETWORK` | `messenger` | не менять |
| `OWNER_IDS` | ваш userId | знаете — впишите; не знаете — ниже, `./contacts.sh` |
| `ORG_CODES` | коды организации через запятую | первые четыре буквы обозначений в вашем журнале: `АБВГ.301121.001` дает `АБВГ` |
| `POSTGRES_DB`, `POSTGRES_USER` | оставить `doc_registry` | |
| `POSTGRES_PASSWORD` | пароль базы | строка от `openssl rand -hex 24` |
| `BACKUP_DIR_1`, `BACKUP_DIR_1_NAME` | оставить `./backups` и `Основная` | папка 1 для копий из чата: `E:\doc-registry-bot\deploy\backups` |
| `BACKUP_DIR_2`, `BACKUP_DIR_3` | пусто | еще одна папка для копий, если нужна: шаг 14 |
| `BACKUP_REMINDER_DAY`, `BACKUP_REMINDER_TIME`, `BACKUP_REMINDER_ZONE` | оставить: понедельник, 10:00, Москва | напоминание сделать копию; `нет` в первой строке выключает его (шаг 14) |
| `BACKUP_SHARE`, `BACKUP_SHARE_USER`, `BACKUP_SHARE_PASSWORD`, `BACKUP_SHARE_DOMAIN` | на ПК пусто: сотрите значения после `=` | |

Сохраните: `Ctrl+S`. Строку `BOT_DIR` (папка бота) скрипты допишут в `.env` сами, ее не трогайте.

**Изменили `.env` позже**, когда бот уже работает: примените командой

```bash
cd /mnt/e/doc-registry-bot/deploy
docker compose up -d
```

Простой `docker compose restart` новый `.env` не перечитает. Строки `POSTGRES_*` после первого
запуска не меняйте (ниже).

**Свой userId.** Если не знаете его, сохраните `.env` с остальными строками (`BOT_VERSION` уже
заполнена) и выполните (вместо `Фамилия` — ваша фамилия):

```bash
cd /mnt/e/doc-registry-bot/deploy
docker load -i ../dist/doc-registry-bot-1.3.0.tar.gz
./contacts.sh | grep Фамилия
```

`docker load` загружает образ бота из файла шага 5 (в конце строки `Loaded image: ...`):
`contacts.sh` работает через него. Без этой команды будет ошибка `pull access denied for
doc-registry-bot`. Делается один раз; `update.sh` в шаге 10 загрузит файл еще раз, это не мешает.

Ответ вида `123456;Фамилия Имя Отчество`: число слева впишите в `OWNER_IDS` и сохраните `.env`.
Себя в списке нет: добавьте учетную запись бота в свои контакты в мессенджере и повторите.
`Ошибка: служба мессенджера недоступна` — вернитесь к шагу 6 и проверьте `MESSENGER_URL`.

**Как создается база PostgreSQL.** Ставить PostgreSQL не нужно ни в Windows, ни в Ubuntu: он
работает в Docker. При первом запуске (`./backup.sh` в шаге 9 или `./update.sh` в шаге 10) Docker
сам создает пустую базу `POSTGRES_DB`, пользователя `POSTGRES_USER` с паролем `POSTGRES_PASSWORD`
из `.env`. Таблицы бот создает сам. Данные лежат внутри Docker, в томе `doc-registry-bot_db-data`,
а не на диске E:. Они переживают перезапуски, перезагрузки и обновления; стирает их только
удаление этого тома (шаг 16).

Пароль базы вводить не придется никогда: бот и копии берут его из `.env`. Поэтому:

- строки `POSTGRES_*` заполните до первого запуска: потом база их не перечитывает;
- в пароле не должно быть `$` и пробелов (у `openssl rand -hex 24` их нет);
- `.env` не удаляйте: без этого пароля бот к базе не подключится.

## 8. Один бот на учетную запись

Бот на ПК работает с рабочей учетной записью бота. Пока он включен, никто другой от имени этой
учетной записи отвечать не должен (и бот на сервере тоже), иначе на одно сообщение будет две
регистрации.

1. Положите файл журнала, например, в `E:\bot-files\журнал.csv`. Нужен CSV или книга Excel, в

   ФИО регистрирующего, Подразделение регистрирующего, Актуальность, Отметка учета,
   Примечание первичное, Примечание краткая характеристика.
2. В терминале VS Code:

   ```bash
   cd /mnt/e/doc-registry-bot/deploy
   ./backup.sh
   ./import.sh /mnt/e/bot-files/журнал.csv
   ```

3. `import.sh` проверит файл («Файл годится, записей: N.») и спросит «Продолжить? (да/нет)».
   Наберите `да`. Ответ «Журнал заменен. Было записей: 0, стало: N.» — журнал в базе.

Если в файле ошибки, `import.sh` перечислит строки и ничего не загрузит. Исправьте файл и
повторите обе команды (`./backup.sh` и `./import.sh`).

## 14. Резервные копии

Копия — два файла, снятые в один момент: `база-<дата_время>.dump` (вся база: журнал, доступы,
администраторы, журнал действий) и `журнал-<дата_время>.csv` (журнал КД). Копия сделана, только
если созданы оба файла. Старые копии бот не удаляет никогда: лишние удаляйте сами.

**Копия через мессенджер** (только главный администратор, то есть владелец из `OWNER_IDS`):

1. Напишите боту «Резервная копия».
2. Бот покажет папку по умолчанию (папка 1, `E:\doc-registry-bot\deploy\backups`) и список
   разрешенных папок. Ответьте «Да», чтобы сохранить в папку по умолчанию, или номер (имя, путь)
   другой папки из списка: бот покажет ее и спросит еще раз. «Нет» отменяет копию.
3. Итог придет отдельным сообщением: по каждому файлу, создан ли он, имя и размер, и полный путь
   папки.

Можно сразу указать подпапку внутри разрешенной папки, например
«Резервная копия: E:\doc-registry-bot\deploy\backups\2026»: ее бот создаст сам.

**Копия из терминала** работает по-прежнему, даже когда бот остановлен: `./backup.sh` (шаг 13).

**Еще одна папка для копий**, например `E:\Копии`. Боту доступны только папки из `.env`
(`BACKUP_DIR_1`, `BACKUP_DIR_2`, `BACKUP_DIR_3`) и их подпапки, других папок компьютера он не
видит. Папку создайте сами и положите в нее файл-метку `.doc-registry-copies`:

```bash
mkdir -p /mnt/e/Копии
touch /mnt/e/Копии/.doc-registry-copies
```

Метка нужна вот зачем: если диска нет, Docker подставляет вместо папки пустую, и копия ушла бы
не туда. Без метки бот откажется писать в папку и скажет почему. Затем в `deploy\.env`:

```text
BACKUP_DIR_2=/mnt/e/Копии
BACKUP_DIR_2_NAME=Архив
```

Путь пишется так, как его видит Ubuntu: `E:\Копии` это `/mnt/e/Копии`, папки через `/`. Сохраните
и примените:

```bash
cd /mnt/e/doc-registry-bot/deploy
docker compose up -d
```

В мессенджере на «Резервная копия» в списке появится `2. Архив (E:\Копии)`. Папку на диске,
который подключается не всегда (флешка, внешний диск), не задавайте: Ubuntu видит только диски,
подключенные до ее запуска.

**Напоминание.** Раз в неделю (по умолчанию в понедельник в 10:00 по Москве) бот пишет главному
администратору: «Необходимо сделать резервную копию. Сделать сейчас? Да / Нет».

- «Да»: выбор папки, как при команде «Резервная копия». «Нет»: копия на этой неделе не делается.
- Ответить можно в течение 24 часов.
- Если ПК был выключен в это время, напоминание придет одно, после запуска бота. Повторный
  запуск бота не дает второго напоминания.
- Если после «Да» копия не сделана (отменили, ошибка, не ответили 10 минут), напоминание придет
  снова, всем главным администраторам, примерно через 11 минут после «Да».
- Если копию на этой неделе уже сделали после времени напоминания (в мессенджере или
  `./backup.sh`), напоминание не придет.
- День, время и часовой пояс меняются в `.env` (`BACKUP_REMINDER_DAY`: `пн`…`вс` или `нет`,
  `BACKUP_REMINDER_TIME`: `10:00`, `BACKUP_REMINDER_ZONE`: пусто для Москвы) и применяются
  командой `docker compose up -d`.

**Несколько главных администраторов** (`OWNER_IDS=111,222`): напоминание приходит всем в порядке
`OWNER_IDS`. Первый ответ закрывает его у всех, остальным бот пишет, кто ответил и что делает.
Операцию подтверждает тот, кто ее начал; итог приходит ему, а итог копии по напоминанию коротко
и остальным.

**Замена всего журнала через мессенджер** (только главный администратор):

1. Сделайте копию («Резервная копия» или `./backup.sh`). Для замены она годится 30 минут, если
   журнал с тех пор не менялся.
2. Отправьте боту сообщение «Заменить журнал» и приложите к нему файл журнала `.csv` (другие
   форматы не принимаются).
3. Бот проверит файл по тем же правилам, что `./import.sh`. Есть ошибки: перечислит строки и
   ничего не изменит. Нет ошибок: покажет число записей, предупредит, что журнал будет заменен
   целиком, и спросит «Да» или «Нет».
4. После «Да» бот еще раз проверит копию (оба файла на месте и читаются, копия не старше 30
   минут, журнал не изменился) и заменит журнал. Итог: «Журнал КД заменен. Было записей: N,
   стало: M.».

Доступы, администраторы и журнал действий при замене не меняются. Регистрации, пришедшие во
время замены, ждут ее окончания. Повторная замена требует новой копии. Вернуть журнал из копии:
так же «Заменить журнал» с файлом `журнал-....csv` из копии.

**Восстановить всю базу из копии** (только при беде: записи после копии пропадут):

```bash
cd /mnt/e/doc-registry-bot/deploy
./update.sh --restore backups/база-2026-11-11_101500.dump
```

Копию из другой разрешенной папки указывайте путем Ubuntu:
`./update.sh --restore /mnt/e/Копии/база-2026-11-11_101500.dump`. Скрипт проверит, что копия
читается, спросит «Продолжить? (да/нет)», перед восстановлением сам сделает защитную копию
нынешней базы, затем перезапустит бота. Сообщения, на которые бот ответил до восстановления,
повторно не выполняются.

После успешной загрузки в восстановленную базу записывается действие «Восстановление из
резервной копии»: время, файл и исполнитель «администратор сервера» (ID 0). Затем запускается
бот. Если записать действие и отметку восстановления не удалось, бот остается остановленным.

**Защитные копии.** Перед каждым обновлением (`./update.sh`) скрипт сам делает копию базы в томе
Docker. Список: `docker compose exec backup ls -l /backups`. Они тоже не удаляются.

**Что проверено и ограничения** (версия 1.2.0):

- проверено автоматическими тестами на PostgreSQL: копия через чат (оба файла из одного снимка),
  отказ при недоступной папке, права (только главный администратор), напоминание (одно после
  простоя, без повторов при перезапуске, повтор после «Да» без копии), замена журнала (отказ без
  свежей копии, после изменения журнала, при поврежденной копии, одновременные запросы,
  регистрации во время замены);
- проверено на стенде Docker с подделкой мессенджера: копия в папку и подпапку, восстановление
  DUMP в отдельную базу (совпадает с CSV и журналом), обновление с 1.1.0 и откат, восстановление
  `./update.sh --restore`, напоминание двум владельцам;
- не проверено: пути Windows на настоящем ПК, настоящая сетевая папка, настоящий мессенджер.
  Проверьте у себя первую копию в каждую папку и замену журнала на тестовой учетной записи;
- старые копии бот не удаляет, место освобождайте сами; через мессенджер заменяется только весь
  журнал и только файлом CSV; всю базу восстанавливает только `./update.sh --restore`; диски,
  подключаемые на время, не поддерживаются.

## 15. Каждый день

- Бот работает в том же Docker, что и служба мессенджера, и поднимается вместе с ним.
- Docker Desktop: запускается сам при входе в Windows, если в **Settings → General** отмечено
  **Start Docker Desktop when you sign in**.
- Docker внутри Ubuntu: запускается, когда запущена Ubuntu. После включения ПК откройте окно
  Ubuntu или терминал в VS Code — поднимутся и служба мессенджера, и бот.
- Пока ПК выключен или спит, бот не отвечает. Сообщения за это время (до 24 часов) он прочитает
  и обработает, когда ПК проснется.
- Журнал работы бота: `cd /mnt/e/doc-registry-bot/deploy && docker compose logs -f bot` (выйти:
  `Ctrl+C`).
- Состояние: `cd /mnt/e/doc-registry-bot/deploy && docker compose ps`.
- Раз в неделю бот напомнит сделать резервную копию (шаг 14): ответьте «Да» и выберите папку.
  Ночной копии по расписанию нет.

## 16. Остановка

```bash
cd /mnt/e/doc-registry-bot/deploy
docker compose stop bot        # остановить бота, база и данные остаются
docker compose start bot       # запустить снова
docker compose down            # остановить все контейнеры бота, данные остаются
```

После проверки сохраните журнал (шаг 13) и остановите бота: `docker compose stop bot`.

Удалить тестовую базу (журнал и доступы пропадут безвозвратно):

```bash
cd /mnt/e/doc-registry-bot/deploy
docker compose down
docker volume rm doc-registry-bot_db-data
```

Удаляется только база. Защитные копии в томе Docker, файлы в `deploy\backups` и в других папках
копий остаются. Служба мессенджера и сеть `messenger` не трогаются. Команду
`docker compose down -v` не используйте: она удалит и защитные копии.

## 17. Обновление на ПК

Бот уже установлен, в `deploy` есть ваш `.env`. Выберите один способ ниже: со сборкой на ПК
или со скачиванием готовой сборки. Команды выполняйте по порядку в Ubuntu/WSL; при ошибке
остановитесь. В примерах проект `E:\doc-registry-bot` и версия `1.3.0`: подставьте свою папку
и номер версии из имени архива.

### Вариант 1. Собрать на ПК и установить

1. Обновите код и скрипты:

   ```bash
   cd /mnt/e/doc-registry-bot
   git switch master
   git pull --ff-only origin master
   ```

2. Запустите отдельную базу для тестов и проверьте готовность:

   ```bash
   docker compose -f tests/compose.yaml up -d
   docker compose -f tests/compose.yaml exec -T postgres pg_isready -U postgres -d drb_test
   ```

   Должно быть `accepting connections`. Если база еще запускается, повторите вторую команду
   через несколько секунд.

3. Запустите проверки и сборку:

   ```bash
   scripts/build.sh
   ```

   В итогах тестов не должно быть `failed` или `skipped`. Дождитесь строки
   `Собрано: dist/doc-registry-bot-1.3.0.tar.gz`. Artifacts скачивать не нужно.

4. Установите собранную версию:

   ```bash
   cd /mnt/e/doc-registry-bot/deploy
   ./update.sh ../dist/doc-registry-bot-1.3.0.tar.gz
   ```

   Скрипт загрузит образы, проверит настройки, сделает защитную копию базы, перезапустит бота и
   проверит его версию. Дождитесь строки `Бот работает, версия 1.3.0.`.

5. Напишите боту «Журнал действий». В CSV должна быть запись «Выгрузка журнала действий».
   Новые регистрации тоже будут попадать в этот журнал, по одной записи на документ.

### Вариант 2. Скачать из GitHub Actions и установить

1. Обновите код и скрипты:

   ```bash
   cd /mnt/e/doc-registry-bot
   git switch master
   git pull --ff-only origin master
   ```

2. Откройте https://github.com/rvburov/doc-registry-bot/actions и войдите в GitHub. Выберите
   последний запуск «Проверки» ветки `master` и дождитесь зеленой галочки. Внизу страницы
   нажмите **Artifacts → doc-registry-bot-1.3.0** (или номер вашей версии). Версия должна
   совпадать с `version` в полученном `pyproject.toml`.
3. Распакуйте скачанный ZIP в Проводнике в `E:\doc-registry-bot\dist`. Проверьте, что получился
   файл `E:\doc-registry-bot\dist\doc-registry-bot-1.3.0.tar.gz`, без дополнительной вложенной
   папки. Сам `.tar.gz` не распаковывайте; `scripts/build.sh` здесь не требуется.
4. Проверьте файл в Ubuntu/WSL:

   ```bash
   ls -lh /mnt/e/doc-registry-bot/dist/doc-registry-bot-1.3.0.tar.gz
   ```

5. Установите скачанную сборку:

   ```bash
   cd /mnt/e/doc-registry-bot/deploy
   ./update.sh ../dist/doc-registry-bot-1.3.0.tar.gz
   ```

   Скрипт загрузит образы, проверит настройки, сделает защитную копию базы, перезапустит бота и
   проверит его версию. Дождитесь строки `Бот работает, версия 1.3.0.`.

6. Напишите боту «Журнал действий». В CSV должна быть запись «Выгрузка журнала действий».
   Новые регистрации тоже будут попадать в этот журнал, по одной записи на документ.

Откат на прежнюю версию (из папки `deploy`): `./update.sh --rollback`.

Файл для сервера — тот же `dist/doc-registry-bot-<версия>.tar.gz`, отправка по `scp` из этого же
терминала: [server.md](server.md), шаг 6.

В версии 1.3.0 миграция автоматически добавляет подразделение и актуальность без удаления
записей. Старые записи получают актуальность «Зарегистрирован» и пустое подразделение;
новые регистрации получают подразделение из карточки API. Выгрузки содержат десять столбцов.
Новые настройки в `.env` для этого не нужны.

**`.env` при обновлении не трогайте.** `update.sh` берет ваш `deploy\.env` (пароль базы,
`OWNER_IDS`, адрес службы), сам меняет `BOT_VERSION` и служебный путь `BOT_DIR`. `.env.example`
из архива — только образец: не копируйте его поверх `.env`, иначе пропадут настройки и пароль базы. Журнал и
пользователи хранятся в базе в Docker и при обновлении остаются.

- `compose.yaml` и скрипты в `deploy` обновляет `git pull`, копировать их из архива не нужно.
- Новые строки версии 1.2.0 (`BACKUP_DIR_*`, `BACKUP_REMINDER_*`) не обязательны: без них копии
  идут в `deploy\backups`, напоминание в понедельник в 10:00 по Москве. Нужны другие — шаг 14.
- Строки `BACKUP_TIME` и `BACKUP_KEEP_DAYS` больше не используются, их можно удалить.

## 18. Если не получается

| Что видно | Что сделать |
|---|---|
| `docker: command not found` | шаг 2 |
| `permission denied` и `docker.sock` | `sudo usermod -aG docker $USER`, закройте терминал, откройте снова |
| `network messenger ... not found` | шаг 6 |
| `Ошибка: нет файла .env` | вы не в рабочей папке: `cd /mnt/e/doc-registry-bot/deploy` |
| `build.sh`: `Failed to download` | сеть закрывает pypi.org: файл не собирайте, а скачайте (шаг 5) |
| тесты в `build.sh` падают на базе | `docker compose -f tests/compose.yaml up -d` в папке проекта |
| `$'\r': command not found` | код скачан в Windows со старыми переводами строк: в папке проекта `git rm -rq --cached . && git reset -q --hard` (ваши правки в коде пропадут) |
| `git pull` пишет об изменениях, которых вы не делали | `git config core.fileMode false` и повторите |
| бот запущен, но не отвечает | `docker compose logs bot`; шаг 6 и `MESSENGER_URL` в `.env` |
| бот пишет `password authentication failed` | пароль в `.env` поменяли после первого запуска: верните прежний. На ПК для теста можно начать с чистой базы: шаг 16, удалить тестовую базу (журнал и доступы пропадут) |
| `./contacts.sh`: `Ошибка: служба мессенджера недоступна` | шаг 6 и `MESSENGER_URL` в `.env` |
| `No such file or directory` для файла из Windows | путь начинается с `/mnt/` и буквы диска (`/mnt/e/`), папки через `/`, имя с пробелами — в кавычках |
| папки `/mnt/e` нет | диск сетевой или съемный: `sudo mkdir -p /mnt/e && sudo mount -t drvfs E: /mnt/e` |
| в итоге копии «нет файла-метки .doc-registry-copies» | по порядку: проверьте, что диск подключен (`ls` папки); если подключили после запуска бота, `docker compose restart backup`; только если папка новая и диск на месте, создайте метку (шаг 14) |
| «Папка ... недоступна боту» | папки нет в `.env`: шаг 14, `BACKUP_DIR_2` и `docker compose up -d` |
| «контейнер копий не ответил» | `docker compose ps`: строки `backup` нет или она не `running`, выполните `docker compose up -d` |
