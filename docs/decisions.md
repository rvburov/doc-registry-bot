# Регистрация КД: решения и план

Итог обсуждения с пользователем 10.11.2026. Решения здесь не переигрываются без пользователя.

## 1. Что это

- Независимая программа «Регистрация КД»: бот в корпоративной программе-мессенджере выдает
  обозначения по ГОСТ 2.201-80 и ведет журнал регистрации.
- Своя база PostgreSQL, запуск только в Docker. Окна нет, все управление — командами в боте.
- Других программ в работе нет. Журнал КД живет только в базе бота, данные отдаются выгрузкой CSV
  по команде.
- Язык — Python. Поведение задано тестами-примерами «сообщение → ожидаемый ответ»: код пишется,
  пока они не пройдут, ожидания в них не меняются.

## 2. Стек

| Задача | Чем |

| База | PostgreSQL; SQLAlchemy 2 + psycopg 3; миграции Alembic |

| Excel | `openpyxl` |

| Журнал программы | встроенный `logging` в stdout |

| Проверка кода | `ruff` (оформление, стиль, «одна дверь» в сеть), `mypy` |

FastAPI не нужен: бот ничего не принимает по HTTP. Понадобится веб-страница администратора — тогда
и добавить. Скрипты сборки и обновления — bash.

## 3. Установка

На сервере два независимых `compose`:

| Что | Чье |
|---|---|
| Служба мессенджера (API для ботов, порт 8888) | готовый контейнер, свой `compose` |
| `bot` — программа | наш `deploy/compose.yaml` |
| `postgres` — база; данные на томе сервера, порт наружу не открыт | наш |
| `backup` — контейнер копий: копии по заявке бота (`pg_dump`) в разрешенные папки и сетевую папку, защитная копия перед обновлением | наш |

- Связь бота со службой мессенджера — через общую сеть Docker `messenger`: она создается один
  раз, служба подключается к ней под постоянным именем `messenger-api`, бот — своим `compose`.
  Бот обращается к службе по этому имени, оно не зависит от имени контейнера службы.
- У службы мессенджера нет авторизации: кто до нее достучится, пишет от имени бота. Боту ее порт
  8888 не нужен. По решению пользователя порт пока остается открытым: к службе подключаются
  другие программы с компьютеров сети. Как посмотреть подключенных и закрыть порт —
  [server.md](server.md), шаг 13.
- `restart: unless-stopped`: после перезагрузки сервера и после сбоя контейнеры поднимаются сами.
- Время сервера — московское.

`.env` лежит только на сервере, в Git не попадает; читать его может только администратор сервера:

```
BOT_VERSION=1.2.0                          # выставляет update.sh
MESSENGER_URL=http://messenger-api:8888
MESSENGER_NETWORK=messenger                # общая сеть Docker со службой мессенджера
OWNER_IDS=123456
ORG_CODES=АБВГ,ДЕЖЗ
POSTGRES_DB=doc_registry                   # имя базы бота
POSTGRES_USER=doc_registry                 # пользователь базы
POSTGRES_PASSWORD=...                      # пароль без $ и пробелов
BACKUP_DIR_1=./backups                     # папки для копий из чата, до трех, с именами
BACKUP_DIR_1_NAME=Основная
BACKUP_DIR_2=/mnt/e/Копии                  # путь, как его видит Docker (E:\Копии в WSL)
BACKUP_DIR_2_NAME=Архив
BACKUP_DIR_3=
BACKUP_DIR_3_NAME=Папка 3
BACKUP_REMINDER_DAY=пн                     # еженедельное напоминание; нет — выключено
BACKUP_REMINDER_TIME=10:00
BACKUP_REMINDER_ZONE=                      # пусто — Europe/Moscow
BACKUP_SHARE=//сервер/папка
BACKUP_SHARE_NAME=Сетевая папка
BACKUP_SHARE_USER=...
BACKUP_SHARE_PASSWORD=...
BACKUP_SHARE_DOMAIN=
BOT_DIR=/opt/doc-registry-bot              # дописывают update.sh и backup.sh
```

Боту из `.env` передаются только его настройки: пароль сетевой папки видит лишь контейнер копии.

- Токена нет: служба мессенджера работает без авторизации.
- `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` заполняются до первого запуска: PostgreSQL
  читает их один раз, когда создает базу. Их получают база, бот и контейнер копии. Адреса базы
  в `.env` нет: база в том же compose, бот находит ее по имени `postgres`.
- `OWNER_IDS` — числовой `userId` из карточки мессенджера; можно несколько через запятую.
- После правки `.env` — `docker compose up -d` (простой `restart` новый `.env` не перечитает).
- Неверное значение (код организации латиницей или не из 4 букв, нечисловой ID) — бот не
  запускается и пишет причину в журнал.

## 4. Связь с мессенджером

Как устроена связь:

- поток событий — STOMP поверх WebSocket, путь `/notify`, тема `/topic/messages`, события в `data`;
- обрабатываются только события `INCOMING_MESSAGE`; повторы отсекаются по `serverMessageId`;
- ответ — `PUT /message`: `targetId` = `ownerId` отправителя, `targetType` = `person`; перенос
  строки в тексте ответа — `<br>`;
- при сбое отправитель получает «Не удалось обработать сообщение»;
- вложение — `POST /message/download` (`serverMsgId`, `serverFileId`); из сообщения берется один
  файл; имя — из ответа сервера, если его нет — «Вложение.xlsx»; готовности файла бот ждет до
  30 секунд;
- ФИО и карточка отправителя — `GET /user/{userId}`, список контактов — `GET /users`;
- рассылка с файлами — создание сообщения со списком файлов и загрузка файлов блоками
  (`/message/file`, заголовок `Upload-Offset`).

**Сообщения за время простоя.** После каждого подключения к потоку (при запуске и после обрыва)
бот дочитывает историю (`/message/history`) каждого контакта после последнего обработанного
сообщения. Отметка — время сервера мессенджера в его единицах, хранится в базе. Свежие сообщения
обрабатываются через ту же очередь, по одному. Старше 24 часов не выполняются: человек получает
«Сообщение пришло, пока бот не работал. Отправьте его заново.» При самом первом запуске отметки
нет и история не читается: бот отвечает на сообщения, пришедшие после запуска.

**Защита от повтора.** Отметка «сообщение обработано» пишется в той же транзакции, что и его
результат: повторная доставка или дочитывание не выполняют сообщение второй раз.

## 5. Роли

| Роль | Откуда | Может |
|---|---|---|
| Владелец (в текстах бота «главный администратор») | `OWNER_IDS` в `.env`; командой бота не снимается | все, плюс назначать и снимать администраторов, резервная копия и замена журнала через чат |
| Администратор | назначает владелец командой | доступ, выгрузка, отправка сообщений, журнал действий; все администраторы равны |
| Пользователь с доступом | выдает администратор | регистрация, просмотр, изменение, удаление |

Владелец и администраторы регистрировать могут и без отдельной выдачи доступа.

## 6. Команды

Русскими словами без косой черты, в начале сообщения; двоеточие после команды можно ставить.

| Кто | Команды |
|---|---|
| Все с доступом | регистрация, «Просмотр», «Удаление», «Изменение» (сообщения по образцу); «Да», «Нет»; «Инструкция»; «Помощь» |
| Администраторы | «Инструкция администратора», «Выдать доступ», «Удалить доступ», «Отправить инструкцию», «Пользователи», «Выгрузить журнал», «Журнал действий», «Отправить сообщение» |
| Владелец | все команды выше и «Инструкция главного администратора», «Назначить администратора», «Снять администратора», «Администраторы», «Резервная копия», «Заменить журнал» (с файлом CSV) |

**Люди в командах — только полное ФИО или ID**, несколько через запятую. Часть ФИО («Иванов») не
принимается: легко попасть не в того человека. Полное ФИО ищется среди контактов бота без учета
регистра и написания буквы «е». Если полное ФИО совпало у двух человек, бот не выбирает сам:
показывает их ID и отдел и просит повторить команду с ID.

**Перед любой командой о людях бот показывает, кого нашел** (ФИО, ID, отдел), и ждет ответа в
течение 10 минут:

- «Выдать доступ»: «Да» — доступ и инструкция; «Без инструкции» — только доступ (для переезда);
  «Нет» — отмена;
- «Удалить доступ», «Отправить инструкцию», «Назначить администратора», «Снять администратора»,
  «Отправить сообщение»: «Да» или «Нет».

**Отчет о доставке.** Инструкцию при выдаче доступа и по команде «Отправить инструкцию» бот
отправляет сразу и сообщает итог: «Инструкция отправлена: 2 из 3. Не дошла: …» с причиной
(например, бота нет в контактах человека). Запрос на добавление бота в контакты бот не
отправляет (решение пользователя 11.11.2026). «Отправить инструкцию» — только тем, у кого есть
доступ.

**Отправить сообщение:**

```
Отправить сообщение: Иванов Иван Иванович, 123456
Сообщение: Завтра собрание в 10:00.
```

Текст после «Сообщение:» можно продолжить на следующих строках, файлы прикладываются к этому же
сообщению. «Отправить сообщение: всем» — всем, у кого есть доступ. Без строки «Сообщение:» бот не
отправляет. Итог: «Отправлено: N из N» и кому не дошло.

- «Помощь» показывает каждому только его команды. Команда администратора от человека без прав —
  ответ «нет прав», ничего не выполняется.
- «Выгрузить журнал» — CSV всего журнала КД. «Журнал действий» — последние 10 записей и CSV за год.
- «Инструкция администратора» — правила и примеры команд администратора; «Инструкция главного
  администратора» — команды владельца: администраторы, резервная копия, напоминание, замена
  журнала. Получается три инструкции: пользователя, администратора и главного администратора
  (решение пользователя 12.11.2026).

## 7. Регистрация

Что умеет:

- разбор сообщения «Действие / Номер / Наименование / Проект», маски `ХХХ` и `001-ХХ`, список до
  100 номеров;
- книга Excel вложением (до 10 МБ и 1000 строк), файл с произвольным сообщением;
- справочник ЕСКД, сборка обозначения, подтверждение первого документа серии;
- «Да/Нет» в течение 10 минут, оформление ответов, текст «Инструкции»;
- ФИО регистратора из карточки мессенджера.

Меняется:

- журнал — таблица PostgreSQL с 8 столбцами: Наименование, Обозначение, ФИО регистрирующего,
  Дата регистрации, Проект, Отметка учета, Примечание (первичное применение), Примечание (краткая
  характеристика). Своих столбцов нет;
- номер выдается в одной транзакции, уникальный индекс на «Обозначение» — повтор невозможен;
- ожидания «Да/Нет», обработанные сообщения и квитанции файлов хранятся в базе и переживают
  перезапуск;
- время хранится в UTC, показывается по Москве.

Удаление и изменение:

- удалять и изменять может любой, у кого есть доступ;
- удалить можно несколько документов одним «Да»: номера через запятую в строке «Номер». Не
  найден хоть один номер — не удаляется ничего. Просмотр и изменение — по одному номеру;
- после удаления номер снова свободен и может быть выдан;
- каждое удаление и изменение — в журнал действий: кто, когда, что было, «было → стало».

Журнал целиком (команды на сервере, в папке установки):

- `./backup.sh` — резерв: журнал КД в `backups/журнал-<время>.csv` (файл делается и для пустого
  журнала) и полная копия базы `backups/база-<время>.dump`. Это же и выгрузка журнала из
  терминала;
- `./import.sh ФАЙЛ` — заменить весь журнал файлом (CSV или Excel, 8 столбцов). Только после
  резерва, сделанного не раньше чем 30 минут назад, и только если журнал с тех пор не менялся:
  резерв записывает отпечаток выгрузки (SHA-256), замена сверяет его с базой в той же
  транзакции, под блокировкой таблицы. Ошибка в любой строке файла — не загружается ничего.
  Перед заменой скрипт проверяет файл и спрашивает «да/нет». Доступы и журнал действий не
  меняются;
- то же через чат (владелец): «Заменить журнал» с файлом CSV во вложении, после свежей копии
  (раздел 9);
- вернуть журнал из резерва — та же замена: `./backup.sh`, затем
  `./import.sh backups/журнал-<время>.csv`. Выгрузка и замена согласованы: журнал после такой
  замены совпадает с резервом байт в байт;
- `./users.sh пользователи.csv` — доступ всем из файла (столбцы ID и ФИО), без инструкции. Права
  администратора не меняются. Ошибка в любой строке — не загружается ничего;
- `./contacts.sh` — контакты учетной записи бота «ID;ФИО»: свой userId для `OWNER_IDS` и заготовка
  файла для `users.sh`; база не нужна, только связь со службой мессенджера;
- файл в контейнер передается через стандартный ввод, папки сервера к контейнеру не
  подключаются; в журнал действий пишется «администратор сервера» и имя файла.

## 8. Журнал действий

- Пишутся: команды администраторов и владельца, выдача и снятие доступа и ролей, рассылки, удаления
  и изменения записей журнала КД, замена журнала и выдача доступа из файла на сервере.
- Хранится 12 месяцев; старше — бот удаляет сам раз в сутки. Нужно дольше — выгрузить в CSV.

## 9. Резервные копии и присмотр

Решения пользователя 12.11.2026 (вопросы 1–5) и что из них следует.

**Копия.** Два файла одним снимком базы: `база-<время>.dump` (`pg_dump -Fc` всей базы: журнал,
доступы, администраторы, журнал действий) и `журнал-<время>.csv` (журнал КД). Бот открывает
транзакцию REPEATABLE READ, экспортирует снимок (`pg_export_snapshot`) и в этой же транзакции
выгружает CSV; контейнер копий делает `pg_dump --snapshot` этим снимком, поэтому файлы совпадают.
Сначала DUMP, затем он читается целиком (`pg_restore -f /dev/null`), затем CSV со сверкой
отпечатка (SHA-256). Копия сделана, только если созданы оба файла; владелец получает итог по
каждому файлу: создан ли, имя, размер, путь.

**Кто и как.** Только владелец (`OWNER_IDS`), командой «Резервная копия»: бот показывает папку по
умолчанию и список, ответ «Да», номер (имя, путь) другой папки или «Нет». Заявка ложится в таблицу
`backup_jobs`, контейнер копий берет ее (`FOR UPDATE SKIP LOCKED`) и пишет итог туда же; бот
отправляет итог из базы, поэтому он доходит и после перезапуска бота. Контейнер отмечается в базе
каждые 10 секунд: остановленный контейнер бот отличает от занятого. Копия из терминала
(`./backup.sh`) идет тем же путем и тоже записывается в базу.

**Папки** (вопросы 3 и 4: «а»). До трех папок в `.env` (`BACKUP_DIR_1..3`) с понятными именами,
выбор номером; папка 1 — по умолчанию (`./backups` рядом с `compose.yaml`). Последней в списке —
сетевая папка Windows (`BACKUP_SHARE`), куда контейнер пишет через `smbclient`, не подключая ее к
Ubuntu. Других папок компьютера бот и контейнер не видят: в контейнер подключены только эти
папки. Подпапки внутри них можно указать в чате. Путь в `.env` — как его видит Docker (`/mnt/e/...`
в WSL, `/srv/...` на сервере), в чате показывается как на компьютере (`E:\...`). Корень диска и
системные папки бот не принимает и не запускается. В каждой папке нужен файл-метка
`.doc-registry-copies`: если диск не подключен, Docker подставил бы пустую папку, и копия ушла бы
не туда. Изменения `.env` применяются командой `docker compose up -d`.

**Ночной копии нет** (вопрос 1: «б»). Остаются еженедельное напоминание и защитная копия перед
обновлением. Старые копии не удаляются нигде: ни на сервере, ни в папках, ни в сетевой папке.
Прежний образ копий (при откате на версию до 1.2.0) получает `BACKUP_KEEP_DAYS=36500`, чтобы не
удалял старые копии; защитную копию перед обновлением делает образ новой версии.

**Напоминание** (вопрос 5). «Необходимо сделать резервную копию. Сделать сейчас? Да / Нет», по
умолчанию в понедельник в 10:00 по Москве (`BACKUP_REMINDER_DAY`, `_TIME`, `_ZONE`; `нет` —
выключено). «Да» — выбор папки, «Нет» — до следующей недели. Ответ действует 24 часа после
напоминания.

- В счет идет только последний наступивший срок: пропущенное, пока бот не работал, приходит одно
  после запуска; пачки за каждую неделю нет. Сроки до первого запуска с напоминанием, до смены
  расписания и пока напоминание было выключено не считаются.
- Состояние в базе (таблица `reminders`, срок и владелец уникальны): доставка отмечается только
  после удачной отправки, неудачная повторяется через 10 минут; перезапуск не дает второго.
- Владелец посреди другой операции «Да/Нет» получает напоминание после нее: его «Да» не должно
  попасть не туда. По той же причине «Да» не засчитывается напоминанию, если после напоминания
  владельцу задали другой вопрос: тогда напоминание повторяется, но только в первые сутки.
- «Да», написанное до напоминания (дочитано после простоя), ответом на него не считается.
- «Да» закрывает напоминание только успешной копией: отмена, ошибка или 10 минут без ответа о
  папке, и через 11 минут после «Да» напоминание снова у всех.
- Успешная копия после срока (из чата или терминала) делает напоминание ненужным: оно не
  приходит.

**Несколько владельцев** (вопрос 2: «а»). Напоминание получают все, в порядке `OWNER_IDS`. Первый
ответ закрывает его у всех, остальным бот пишет «Резервную копию по напоминанию делает ФИО» или
что ответили «Нет». Подтверждает операцию тот, кто ее начал; итог приходит ему, итог копии по
напоминанию коротко и остальным.

**Замена журнала через чат** (вопрос 5). «Заменить журнал» с файлом CSV во вложении; заменяется
весь журнал КД, остальная база не меняется.

- Только CSV, проверка по правилам `./import.sh`; ошибка в любой строке — не меняется ничего.
- Нужна свежая успешная копия: оба файла, не старше 30 минут (как у `import.sh`), журнал с тех
  пор не менялся (отпечаток CSV копии совпадает с журналом).
- Предупреждение «весь журнал будет заменен» и отдельное «Да». Подтвердить может только тот, кто
  прислал файл, и только один раз.
- Перед самой заменой — повторная проверка: копия не устарела, файлы копии на месте и целы
  (контейнер сверяет SHA-256 обоих и читает DUMP целиком), журнал не изменился.
- Замена — одна транзакция под блокировкой журнала (`EXCLUSIVE`); регистрации берут `ROW
  EXCLUSIVE` и ждут ее окончания. Итог: «Было записей: N, стало: M», запись в журнал действий.

**Восстановление** — только из терминала: `./update.sh --restore ФАЙЛ` (копия из `backups/`, из
папки `BACKUP_DIR_N` или защитная). Скрипт проверяет, что копия читается, спрашивает «да/нет»,
делает защитную копию нынешней базы, очищает схему и загружает копию целиком. Отметка
`restored_at`: сообщения, отправленные до остановки бота, при дочитывании не выполняются повторно.

**Присмотр.** Итог защитной копии — `status.json` в томе копий; бот читает его раз в час и пишет
владельцу при сбое. Владельцу приходят: «бот запущен, версия …» при старте; сообщение после
восстановления связи со службой мессенджера, если она пропадала дольше 5 минут.

**Ограничения.** Не проверены на настоящем оборудовании: пути Windows на ПК пользователя,
настоящая сетевая папка, настоящая программа-мессенджер (проверено тестами и стендом с
подделкой). Диски, подключаемые на время (флешка), не поддерживаются: WSL видит диски,
подключенные до его запуска. Место под копии освобождает человек.

## 10. Сборка и доставка

- Образ собирается только на ПК пользователя (Windows; проект на диске Windows, открыт в VS Code;
  команды в терминале Ubuntu внутри WSL, те же, что на сервере, — [pc.md](pc.md)):
  `scripts/build.sh` — проверки → образ `doc-registry-bot:<версия>` → файл
  `doc-registry-bot-<версия>.tar.gz`. Реестры образов не используются.
- На сервер файл попадает по SSH. Установка — `deploy/update.sh <файл>`: копия базы → загрузка
  образа → перезапуск → проверка, что поднялась нужная версия.
- Откат — `deploy/update.sh --rollback`: прежний образ. Миграции только добавляющие, поэтому
  прежняя версия работает и на обновленной схеме, данные не теряются. Восстановление базы из
  копии — отдельная команда `deploy/update.sh --restore ФАЙЛ.dump`, только при беде.
- В файле `dist/doc-registry-bot-<версия>.tar.gz` три образа: бот, копия, PostgreSQL. Образ копии
  построен на образе PostgreSQL, поэтому его слои в файле одни и размер не растет (около 200 МБ).
  На сервер вместе с файлом: `compose.yaml`, `update.sh`, `backup.sh`, `import.sh`, `users.sh`,
  при первой установке `.env.example`.
- У сервера есть интернет для установки Docker и обновлений Ubuntu.
- ПК — тестовый стенд с тестовыми данными. Сервер — виртуальная машина Ubuntu: 2 ядра,
  2–4 ГБ памяти, 20 ГБ диска.
- GitHub — только код и автоматические проверки на каждый коммит.

## 11. Первый запуск и перенос данных

Переносится:

| Что | Как |
|---|---|
| Журнал, 8 столбцов | файл CSV или книга Excel → `./backup.sh`, затем `./import.sh ФАЙЛ` (см. `docs/admin.md`); даты и ФИО сохраняются из файла; повтор обозначения или неразобранная дата останавливают загрузку целиком |
| Список доступа | `./users.sh пользователи.csv` (столбцы ID и ФИО) или командой «Выдать доступ: …» с ответом «Без инструкции» |
| Коды организации | в `.env` |
| Вся база с ПК на сервер | копия `./backup.sh` на ПК → `pg_restore` в базу сервера до первого запуска ([server.md](server.md), шаг 9): журнал, доступы, администраторы, журнал действий и отметка дочитывания |

Историю сообщений до первого запуска бот не дочитывает.

Порядок:

1. Тест на ПК с тестовой учетной записью бота и копией журнала ([pc.md](pc.md)).
2. На сервере — бот с пустой базой, пока выключен; при переезде с ПК — вся база с ПК
   ([server.md](server.md)).
3. Первый запуск: `./backup.sh` и `./import.sh` в базу бота → сверить число записей и последние
   номера нескольких серий → запустить бота → выдать доступ без инструкции (`./users.sh` или
   командой в боте).
4. Остановка при беде: `docker compose stop bot`; журнал с выданными номерами — `./backup.sh`.

С одной учетной записи бота всегда отвечает только один бот: два бота дадут два ответа и две
регистрации.

## 12. Репозиторий

- `rvburov/doc-registry-bot`, основная ветка `master`.
- Агенты работают самостоятельно и отправляют в `master` после зеленых проверок и GitHub Actions,
  без согласования — [AGENTS.md](../AGENTS.md).
- Тесты: примеры логики «сообщение → ожидаемый ответ», тесты базы на настоящем PostgreSQL, подделка
  службы мессенджера для проверки целиком «сообщение → номер → ответ» и дочитывания истории, тест
  текстов бота на запрещенные символы.

## 13. Особенности поведения

- Тексты бота без тире: диапазоны через дефис («001-999»), расшифровка ЕСКД «код: наименование»,
  пустое поле карточки — «не указано».
- ФИО берется из карточки мессенджера для каждой регистрации; неполное ФИО — отказ с объяснением.
- В сообщении с книгой Excel — один файл; несколько файлов — отказ.
- Уникальность обозначения держит индекс базы (без учета регистра и похожей латиницы).
