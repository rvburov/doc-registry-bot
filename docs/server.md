# Регистрация КД: бот на сервере (Ubuntu на виртуальной машине)

Пошагово: проверка и подготовка сервера, связь со службой мессенджера, перенос всей базы с ПК,
запуск, проверка, выгрузка файлов, резервные копии, обновление и остановка. **Каждый шаг
подготовки начинается с проверки:** что уже есть, то не ставится заново. Шаг 2 проверяет весь
сервер сразу и говорит, какие шаги пропустить.

Команды на сервере выполняются в терминале по SSH, команды «на ПК» — в терминале VS Code (Ubuntu,
WSL), как в [pc.md](pc.md). Где выполнять, написано в начале каждого шага.

| Где | Папка | Что |
|---|---|---|
| ПК | `E:\doc-registry-bot` = `/mnt/e/doc-registry-bot` | проект: код, сборка |
| ПК | `E:\doc-registry-bot\deploy` = `/mnt/e/doc-registry-bot/deploy` | бот на ПК (до переезда) |
| ПК | `E:\bot-files` = `/mnt/e/bot-files` | ваши файлы в Windows (диск E:) |
| сервер | `/opt/doc-registry-bot` | рабочая папка бота: `.env`, скрипты, резервы |
| сервер | `/opt/doc-registry-bot/backups` | резервные копии: папка 1 для копий из чата и копии `./backup.sh` |
| сервер | папка службы мессенджера | ее `compose.yaml` (шаг 4 покажет, где) |

В примерах `admin@10.0.0.5` — ваш пользователь и адрес сервера, `1.2.0` — версия бота из строки
из имени файла бота ([pc.md](pc.md), шаг 5).

## 0. Что нужно заранее

- адрес сервера и пользователь Ubuntu с правом `sudo`, пароль от него;
- ваш числовой userId в мессенджере и коды организации (те же, что в `.env` на ПК);
- сетевая папка Windows для резервных копий: путь `//сервер/папка`, пользователь и пароль с
  правом записи. Если ее пока нет, бот работает и без нее;
- файл бота на ПК, скачанный с GitHub в `E:\doc-registry-bot\dist` ([pc.md](pc.md), шаг 5).

## 1. Вход на сервер (на ПК)

```bash
ssh admin@10.0.0.5
```

При первом входе ответьте `yes` на вопрос о ключе сервера и введите пароль. Выйти с сервера:
`exit`.

**Вход без пароля** (по желанию). Если `ssh admin@10.0.0.5` уже пускает без пароля, это сделано,
пропустите. Иначе на ПК проверьте, есть ли ключ:

```bash
ls ~/.ssh/id_ed25519.pub
```

- `No such file or directory`: ключа нет, создайте его (на вопросы отвечайте `Enter`):

  ```bash
  ssh-keygen -t ed25519
  ```

- Файл есть: ключ уже создан, `ssh-keygen` не запускайте (он предложит затереть ключ).

Затем передайте ключ серверу (спросит пароль один последний раз):

```bash
ssh-copy-id admin@10.0.0.5
```

## 2. Проверка сервера и Ubuntu (на сервере)

Вставьте блок целиком:

```bash
. /etc/os-release; echo "Ubuntu: $VERSION_ID"
docker version --format 'Docker: {{.Server.Version}}'
docker compose version
snap list docker 2>/dev/null | grep -w docker
id -nG | grep -qw docker && echo "Группа docker: есть" || echo "Группа docker: нет"
date +'Время: %Z'
docker network inspect messenger --format 'Сеть messenger: {{range .Containers}}{{.Name}} {{end}}'
docker ps --format 'Контейнер: {{.Names}}'
ls -d /opt/doc-registry-bot
```

| Строка вывода | В порядке, если | Иначе |
|---|---|---|
| `Ubuntu: …` | `22.04` или новее | обновите Ubuntu до 22.04 или 24.04 (вне этой инструкции) |
| `Docker: …` | есть версия | `command not found` — шаг 3, установка; `permission denied` — шаг 3, группа |
| `Docker Compose version …` | версия `v2…` или новее | шаг 3, установка |
| строка со словом `docker` от snap | такой строки нет | шаг 3, Docker из snap |
| `Группа docker: …` | `есть` | шаг 3, группа |
| `Время: …` | `MSK` | ниже в этом шаге |
| `Сеть messenger: …` | есть имя службы мессенджера | шаг 4 |
| `Контейнер: …` | среди строк есть служба мессенджера | служба не запущена: запустите ее в ее папке (`docker compose up -d`) |
| `ls: /opt/doc-registry-bot` | папка есть, если бот уже ставился | шаг 5 |

Строки с `command not found` или `No such …` — этого нет, нужен шаг из таблицы.

**Обновления Ubuntu** (по желанию, раз в месяц):

```bash
sudo apt-get update
sudo apt-get upgrade -y
```

Если в обновлении есть пакеты Docker, Docker перезапустится, а вместе с ним на минуту
перезапустятся контейнеры, в том числе служба мессенджера и бот.

**Время не `MSK`:**

```bash
sudo timedatectl set-timezone Europe/Moscow
```

Повторите проверку: `Время: MSK`.

## 3. Docker (только если нет по шагу 2)

Служба мессенджера уже работает в Docker, поэтому обычно Docker есть, и нужна только группа.

**Docker из snap** (в шаге 2 была строка `docker` от snap): с папкой `/opt` такой Docker работать
не будет. Остановитесь: этот случай инструкция не покрывает, Docker нужно ставить заново
отдельно, вместе со службой мессенджера.

**Установка** (в шаге 2 `docker: command not found`):

```bash
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
```

Нет только `docker compose` (в шаге 2 Docker есть, а Compose нет):

```bash
sudo apt-get install -y docker-compose-plugin
```

**Группа `docker`** (в шаге 2 `Группа docker: нет` или `permission denied`), чтобы команды шли
без `sudo`:

```bash
sudo usermod -aG docker "$USER"
exit
```

Зайдите снова (`ssh admin@10.0.0.5`) и повторите проверку из шага 2.

## 4. Связь со службой мессенджера (на сервере)

Бот и служба мессенджера — два отдельных контейнера. Чтобы бот нашел службу, нужна общая сеть
Docker `messenger`, а в ней у службы постоянное имя `messenger-api`. Делается до первого запуска
бота. Служба при этом не останавливается надолго, ее порт и данные не меняются.

Что показала строка `Сеть messenger:` в шаге 2:

| Что видно | Что делать |
|---|---|
| имя службы мессенджера | проверьте имя `messenger-api` (в конце шага); есть — шаг пропустите |
| `Error: No such network` | весь шаг |
| пусто или имени службы нет | весь шаг, кроме создания сети |

Создать сеть (если ее нет):

```bash
docker network create messenger
```

**Имя контейнера мессенджера:** `docker ps --format '{{.Names}}'`, в списке найдите контейнер
службы мессенджера. Во всех командах ниже вместо `ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА` подставьте это имя.

```bash
docker port ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА
docker inspect -f '{{index .Config.Labels "com.docker.compose.project.working_dir"}}' ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА
```

- `docker port` покажет строку вида `8888/tcp -> 0.0.0.0:8888`. Число слева — порт службы внутри
  Docker, он нужен для `MESSENGER_URL` (шаг 7).
- Вторая команда покажет папку, из которой служба запущена (ее `compose.yaml`). Пусто — служба
  запущена без `compose`.

**Служба запущена из compose (папка показана).** Подключение к сети записывается в ее
`compose.yaml` и переживает перезапуски и обновления службы:

```bash
cd ПАПКА_ИЗ_ВЫВОДА
cp compose.yaml compose.yaml.bak
nano compose.yaml
```

В описании службы добавьте раздел `networks` (как ниже), а в конце файла — раздел `networks` с
сетью `messenger`:

```yaml
services:
  ИМЯ_СЛУЖБЫ_В_ФАЙЛЕ:
    # ... все, что уже есть, не трогать, строку ports с 8888 оставить
    networks:
      default:
      messenger:
        aliases:
          - messenger-api

networks:
  messenger:
    external: true
```

- `default:` обязателен: без него служба потеряет связь с соседями по своему `compose`.
- Если у службы уже есть `networks:` списком (строки вида `- имя`), перепишите его в виде выше:
  каждое имя с двоеточием в конце (`имя:`), и добавьте `messenger` с `aliases`.
- Если раздел `networks:` в конце файла уже есть, добавьте в него только `messenger` с
  `external: true`.

Сохраните (`Ctrl+O`, `Enter`, `Ctrl+X`), проверьте и примените:

```bash
docker compose config -q
docker compose up -d
```

`docker compose config -q` ничего не выводит, если файл записан верно. Ошибка — исправьте файл
или верните прежний: `cp compose.yaml.bak compose.yaml`. `docker compose up -d` пересоздает
контейнер службы: на несколько секунд она перестает отвечать.

**Служба запущена без compose (пусто):**

```bash
docker network connect --alias messenger-api messenger ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА
```

Команда включает контейнер мессенджера в сеть `messenger` и дает ему постоянное имя
`messenger-api`, по которому его найдет бот. Если все в порядке, она ничего не выводит.

Если контейнер службы когда-нибудь пересоздадут (обновят), повторите эту команду.

**Проверка:**

```bash
docker network inspect messenger --format '{{range .Containers}}{{.Name}} {{end}}'
docker inspect -f '{{json .NetworkSettings.Networks.messenger.Aliases}}' ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА
```

Первая показывает имя службы, вторая — список имен, в котором есть `"messenger-api"`. Имя
контейнера после `docker compose up -d` могло поменяться: возьмите его снова из `docker ps`.

Порт 8888 службы остается открытым: к службе могут подключаться другие программы с компьютеров
сети. Боту порт не нужен. Как посмотреть, кто подключен, и как закрыть порт потом, — шаг 13.

## 7. Настройки `.env` (на сервере)

```bash
cd /opt/doc-registry-bot
cp -n .env.example .env
chmod 600 .env
chmod +x *.sh
nano .env
```

`cp -n` не трогает `.env`, если он уже есть: тогда только проверьте строки по таблице.

Пароль для базы сервера сгенерируйте заранее и скопируйте выведенную строку:

```bash
openssl rand -hex 24
```

| Строка | Что вписать | Откуда взять |
|---|---|---|
| `BOT_VERSION` | версию, например `1.2.0` | имя файла образов из шага 6 |
| `MESSENGER_URL` | `http://messenger-api:8888` | имя из шага 4; если порт в шаге 4 не `8888` — свой порт |
| `MESSENGER_NETWORK` | `messenger` | не менять |
| `OWNER_IDS` | ваш userId | как в `.env` на ПК; или `./contacts.sh \| grep Фамилия` после шага 8 (нужен загруженный образ) |
| `ORG_CODES` | коды организации | как в `.env` на ПК |
| `POSTGRES_DB`, `POSTGRES_USER` | оставить `doc_registry` | |
| `POSTGRES_PASSWORD` | новый пароль базы сервера | строка от `openssl rand -hex 24`; пароль с ПК не нужен |
| `BACKUP_DIR_1`, `BACKUP_DIR_1_NAME` | оставить `./backups` и `Основная` | папка 1 для копий из чата: `/opt/doc-registry-bot/backups` |
| `BACKUP_DIR_2`, `BACKUP_DIR_3` | пусто | еще одна папка для копий, если нужна: шаг 15 |
| `BACKUP_REMINDER_DAY`, `BACKUP_REMINDER_TIME`, `BACKUP_REMINDER_ZONE` | оставить: понедельник, 10:00, Москва | напоминание сделать копию; `нет` в первой строке выключает его (шаг 15) |
| `BACKUP_SHARE` | сетевая папка `//сервер/папка` | у администратора сети; нет папки — сотрите значение |
| `BACKUP_SHARE_NAME` | оставить `Сетевая папка` | так она называется в списке папок в чате |
| `BACKUP_SHARE_USER`, `BACKUP_SHARE_PASSWORD`, `BACKUP_SHARE_DOMAIN` | учетная запись с правом записи в папку; домен, если нужен | у администратора сети |

Сохраните: `Ctrl+O`, `Enter`, `Ctrl+X`. Строку `BOT_DIR` (папка бота) скрипты допишут в `.env`
сами, ее не трогайте.

**Изменили `.env` позже**, когда бот уже работает: примените командой `docker compose up -d` в
`/opt/doc-registry-bot`. Простой `docker compose restart` новый `.env` не перечитает. Строки
`POSTGRES_*` после шага 9 не меняйте.

**База PostgreSQL** ставится не отдельно, а создается Docker сама в шаге 9
(`docker compose up -d --wait postgres`): пустая база `POSTGRES_DB`, пользователь `POSTGRES_USER`,
пароль `POSTGRES_PASSWORD` из этого `.env`. Копия с ПК потом загружается в нее, поэтому пароль на
сервере свой. Данные лежат в томе Docker `doc-registry-bot_db-data`, стирает их только удаление
этого тома. Команду `docker compose down -v` не используйте: она удалит и базу, и защитные
копии. Строки `POSTGRES_*` заполните до шага 9, в пароле не должно быть `$` и пробелов, `.env`
не теряйте: без пароля бот к базе не подключится.

## 8. Образы (на сервере)

```bash
cd /opt/doc-registry-bot
docker load -i doc-registry-bot-1.2.0.tar.gz
```

В конце три строки `Loaded image: …`: бот, копия, PostgreSQL.

## 9. Перенос всей базы с ПК

Переносится все: журнал, пользователи с доступом, администраторы, журнал действий и место, до
которого бот прочитал сообщения. Шаги 9 и 10 делайте подряд: с остановки бота на ПК до запуска
на сервере бот никому не отвечает. Сообщения за это время бот на сервере прочитает сам после
запуска (за последние 24 часа).

**На ПК** остановите бота и сделайте копию:

```bash
cd /mnt/e/doc-registry-bot/deploy
docker compose stop bot
./backup.sh
```

Запомните из вывода число «записей в журнале» и имя файла `backups/база-<дата_время>.dump`.
Отправьте копию на сервер (имя файла — из вывода):

```bash
scp backups/база-2026-11-12_101500.dump admin@10.0.0.5:/opt/doc-registry-bot/
docker compose down
```

`docker compose down` выключает бота на ПК совсем. **Больше его не запускайте:** два бота на
одной учетной записи дают по два ответа и по две регистрации.

**На сервере** восстановите копию в базу сервера:

```bash
cd /opt/doc-registry-bot
docker compose up -d --wait postgres
docker compose exec -T postgres sh -c 'pg_restore --clean --if-exists --no-owner -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < база-2026-11-12_101500.dump
./backup.sh
```

`./backup.sh` должен показать то же число «записей в журнале», что на ПК. Если что-то пошло не
так, команду `pg_restore` можно повторить: она каждый раз заменяет базу копией целиком.

## 10. Запуск (на сервере)

```bash
cd /opt/doc-registry-bot
./update.sh doc-registry-bot-1.2.0.tar.gz
```

Строка «Бот работает, версия 1.2.0.» означает, что бот запущен. В мессенджер вам придет «Бот
регистрации КД запущен, версия 1.2.0.».

## 11. Проверка

В мессенджере:

1. «Помощь»: список команд.
2. «Пользователи»: те же люди, что были на ПК.
3. «Выгрузить журнал»: файл с тем же числом записей.
4. «Резервная копия», затем «Да»: через несколько секунд придет «Резервная копия сделана», оба
   файла созданы, папка `/opt/doc-registry-bot/backups`.
5. Если задана сетевая папка: «Резервная копия», затем номер строки «Сетевая папка» из списка и
   «Да». Итог «Резервная копия сделана» с путем сетевой папки означает, что запись туда работает.
   «Не сделана» и причина: проверьте `BACKUP_SHARE*` в `.env` и примените `docker compose up -d`.

Перезагрузка сервера (один раз, чтобы убедиться, что бот поднимается сам):

```bash
sudo reboot
```

Через минуту-две вам придет «Бот регистрации КД запущен, версия 1.2.0.».

## 12. Файлы: выгрузка и загрузка

**Выгрузить через мессенджер:** «Выгрузить журнал», «Журнал действий».

**Выгрузить через терминал.** На сервере:

```bash
cd /opt/doc-registry-bot
./backup.sh
```

На ПК (имя файла — из вывода `backup.sh`):

```bash
scp admin@10.0.0.5:/opt/doc-registry-bot/backups/журнал-2026-11-12_101500.csv /mnt/e/bot-files/
```

Файл появится в `E:\bot-files`, открывается в Excel двойным щелчком.

**Загрузить журнал с ПК на сервер** (заменяет весь журнал). На ПК:

```bash
scp /mnt/e/bot-files/журнал.csv admin@10.0.0.5:/opt/doc-registry-bot/
```

На сервере:

```bash
cd /opt/doc-registry-bot
./backup.sh
./import.sh журнал.csv
```

**Пользователи списком:** так же, файлом `пользователи.csv` и командой
`./users.sh пользователи.csv`. Заготовку со всеми контактами бота дает
`./contacts.sh > контакты.csv`. Подробно о замене журнала и списке пользователей:
[admin.md](admin.md), раздел 5.

## 13. Порт 8888 службы мессенджера

Кто сейчас подключен к службе (на сервере; вместо `ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА` — имя контейнера
службы мессенджера из `docker ps`):

```bash
sudo nsenter -t "$(docker inspect -f '{{.State.Pid}}' ИМЯ_КОНТЕЙНЕРА_МЕССЕНДЖЕРА)" -n ss -tn state established '( sport = :8888 )'
```

В столбце `Peer Address` адреса подключенных. `172.…` — бот и другие контейнеры Docker,
остальные адреса — компьютеры сети.

Закрыть порт, когда снаружи к службе никто не подключается: в `compose.yaml` службы удалите строку
с `8888` в разделе `ports` (сделайте копию файла, как в шаге 4) и выполните `docker compose up -d`
в ее папке. Бот продолжит работать: он ходит через сеть `messenger`.

## 14. Каждый день

- Бот и контейнер копий поднимаются сами после перезагрузки сервера.
- Журнал работы бота: `cd /opt/doc-registry-bot && docker compose logs -f bot` (выйти:
  `Ctrl+C`).
- Состояние: `cd /opt/doc-registry-bot && docker compose ps`.
- Владельцу приходят: «бот запущен» при старте, «связь восстановлена» после перерыва дольше 5
  минут, сообщение о сбое защитной копии перед обновлением и раз в неделю напоминание сделать
  резервную копию (шаг 15). Ночной копии по расписанию нет.
- Поменяли `.env`: `docker compose up -d` (простой `restart` новый `.env` не перечитает).

## 15. Резервные копии

Копия — два файла, снятые в один момент: `база-<дата_время>.dump` (вся база: журнал, доступы,
администраторы, журнал действий) и `журнал-<дата_время>.csv` (журнал КД). Копия сделана, только
если созданы оба файла. Старые копии бот не удаляет никогда: ни на сервере, ни в сетевой папке.

**Копия через мессенджер** (только главный администратор, то есть владелец из `OWNER_IDS`):
«Резервная копия». Бот покажет папку по умолчанию (папка 1, `/opt/doc-registry-bot/backups`) и
список разрешенных папок, сетевая папка последней. «Да» сохраняет в папку по умолчанию, номер
(имя, путь) другой папки из списка выбирает ее, «Нет» отменяет. Итог придет отдельным сообщением:
по каждому файлу, создан ли он, имя и размер, и полный путь папки. Можно сразу указать подпапку
внутри разрешенной папки, например «Резервная копия: /opt/doc-registry-bot/backups/2026».

**Копия из терминала** работает по-прежнему, даже когда бот остановлен: `./backup.sh` (шаг 12).

**Еще одна папка для копий на сервере**, например `/srv/копии`. Боту доступны только папки из
`.env` (`BACKUP_DIR_1`, `BACKUP_DIR_2`, `BACKUP_DIR_3`), их подпапки и сетевая папка, других
папок сервера он не видит. Папку создайте от своего пользователя и положите в нее файл-метку
`.doc-registry-copies`:

```bash
sudo install -d -o "$USER" -g "$USER" -m 700 /srv/копии
touch /srv/копии/.doc-registry-copies
```

Метка нужна вот зачем: если диск не подключен, Docker подставляет вместо папки пустую, и копия
ушла бы не туда. Без метки бот откажется писать в папку и скажет почему. Файлы копий получают
владельца метки. Затем в `.env`:

```text
BACKUP_DIR_2=/srv/копии
BACKUP_DIR_2_NAME=Архив
```

и примените: `docker compose up -d`. В мессенджере на «Резервная копия» в списке появится
`2. Архив (/srv/копии)`.

**Сетевая папка** (`BACKUP_SHARE*` в `.env`, шаг 7) подключается не к Ubuntu, а только к
контейнеру копий: файлы уходят туда напрямую. Если файл с таким именем там уже есть, он не
перезаписывается: к имени новой копии добавляется номер.

**Напоминание.** Раз в неделю (по умолчанию в понедельник в 10:00 по Москве) бот пишет главному
администратору: «Необходимо сделать резервную копию. Сделать сейчас? Да / Нет».

- «Да»: выбор папки, как при команде «Резервная копия». «Нет»: копия на этой неделе не делается.
- Ответить можно в течение 24 часов.
- Если бот был остановлен в это время, напоминание придет одно, после запуска. Повторный запуск
  бота не дает второго напоминания.
- Если после «Да» копия не сделана (отменили, ошибка, не ответили 10 минут), напоминание придет
  снова, всем главным администраторам, примерно через 11 минут после «Да».
- Если копию на этой неделе уже сделали после времени напоминания (в мессенджере или
  `./backup.sh`), напоминание не придет.
- День, время и часовой пояс: `BACKUP_REMINDER_DAY` (`пн`…`вс` или `нет`),
  `BACKUP_REMINDER_TIME` (`10:00`), `BACKUP_REMINDER_ZONE` (пусто для Москвы), затем
  `docker compose up -d`.

**Несколько главных администраторов** (`OWNER_IDS=111,222`): напоминание приходит всем в порядке
`OWNER_IDS`. Первый ответ закрывает его у всех, остальным бот пишет, кто ответил и что делает.
Операцию подтверждает тот, кто ее начал; итог приходит ему, а итог копии по напоминанию коротко
и остальным.

**Замена всего журнала через мессенджер** (только главный администратор): сначала свежая копия
(«Резервная копия» или `./backup.sh`, годится 30 минут, если журнал с тех пор не менялся), затем
сообщение «Заменить журнал» с файлом журнала `.csv` во вложении. Бот проверит файл по тем же
правилам, что `./import.sh`, предупредит, что журнал будет заменен целиком, и спросит «Да» или
«Нет». После «Да» еще раз проверит копию (оба файла на месте и читаются, копия не старше 30
минут, журнал не изменился) и заменит журнал. Итог: «Журнал КД заменен. Было записей: N, стало:
M.». Доступы, администраторы и журнал действий не меняются; регистрации во время замены ждут ее
окончания.

**Восстановить всю базу из копии** (только при беде: записи после копии пропадут):

```bash
cd /opt/doc-registry-bot
./update.sh --restore backups/база-2026-11-11_101500.dump
```

Копию из другой разрешенной папки указывайте ее путем: `./update.sh --restore
/srv/копии/база-2026-11-11_101500.dump`. Копию из сетевой папки сначала перенесите в `backups/`:
на ПК скопируйте файл из сетевой папки в `E:\bot-files` (Проводник), затем
`scp /mnt/e/bot-files/база-2026-11-11_101500.dump admin@10.0.0.5:/opt/doc-registry-bot/backups/`.
Скрипт проверит, что копия читается, спросит «Продолжить? (да/нет)», сам сделает
защитную копию нынешней базы, восстановит и перезапустит бота. Сообщения, на которые бот ответил
до восстановления, повторно не выполняются.

После успешной загрузки в восстановленную базу записывается действие «Восстановление из
резервной копии»: время, файл и исполнитель «администратор сервера» (ID 0). Затем запускается
бот. Если записать действие и отметку восстановления не удалось, бот остается остановленным.

**Защитные копии.** Перед каждым обновлением (`./update.sh`) скрипт сам делает копию базы в томе
Docker и в сетевой папке. Список на сервере: `docker compose exec backup ls -l /backups`. Они тоже
не удаляются. Восстановление из защитной копии: `./update.sh --restore` и имя файла из списка.

**Что проверено и ограничения** (версия 1.2.0):

- проверено автоматическими тестами на PostgreSQL: копия через чат (оба файла из одного снимка),
  отказ при недоступной папке, права (только главный администратор), напоминание (одно после
  простоя, без повторов при перезапуске, повтор после «Да» без копии), замена журнала (отказ без
  свежей копии, после изменения журнала, при поврежденной копии, одновременные запросы,
  регистрации во время замены);
- проверено на стенде Docker с подделкой мессенджера: копия в папку и подпапку, восстановление
  DUMP в отдельную базу (совпадает с CSV и журналом), обновление с 1.1.0 и откат, восстановление
  `./update.sh --restore`, напоминание двум владельцам;
- не проверено: пути Windows на настоящем ПК, настоящая сетевая папка, настоящий мессенджер.
  Проверьте у себя первую копию в каждую папку и замену журнала на тестовой учетной записи;
- старые копии бот не удаляет, место освобождайте сами; через мессенджер заменяется только весь
  журнал и только файлом CSV; всю базу восстанавливает только `./update.sh --restore`; диски,
  подключаемые на время, не поддерживаются.

## 16. Обновление

На ПК:

```bash
cd /mnt/e/doc-registry-bot
git pull
# новый файл скачать с GitHub в dist, как в pc.md, шаг 5
scp dist/doc-registry-bot-1.3.0.tar.gz dist/*.sh dist/compose.yaml admin@10.0.0.5:/opt/doc-registry-bot/
```

На сервере:

```bash
cd /opt/doc-registry-bot
./update.sh doc-registry-bot-1.3.0.tar.gz
```

`update.sh` сам делает копию базы, загружает образы, перезапускает бота и проверяет версию. Откат
на прежнюю версию: `./update.sh --rollback`. `.env` на сервере не меняйте и `.env.example` поверх
него не копируйте: `update.sh` сам выставит `BOT_VERSION`, остальные настройки и база остаются.

Новую версию до сервера на ПК не запускайте с рабочей учетной записью бота: на сервере в это
время работает бот, ответов будет два. Скачивания файла это не касается.

## 17. Остановка

```bash
cd /opt/doc-registry-bot
./backup.sh                    # журнал со всеми выданными номерами, на всякий случай
docker compose stop bot        # остановить бота, база и данные остаются
docker compose start bot       # запустить снова
```

Восстановление базы из копии (только при беде): шаг 15.

## 18. Если не получается

| Что видно | Что сделать |
|---|---|
| `permission denied` и `docker.sock` | шаг 3, группа `docker`: `exit` и войти снова |
| `network messenger ... not found` | шаг 4: `docker network create messenger` |
| `Ошибка: нет файла .env` | вы не в рабочей папке: `cd /opt/doc-registry-bot` |
| `задайте POSTGRES_PASSWORD в .env` и похожие | заполните строку в `.env` (шаг 7) |
| бот пишет `password authentication failed` | пароль в `.env` поменяли после шага 9: верните прежний |
| «Бот перезапускается» после `update.sh` | `docker compose logs bot`: обычно ошибка в `.env` |
| бот работает, но не отвечает | `docker compose logs bot`; имя и порт в `MESSENGER_URL`; проверка шага 4 |
| служба мессенджера перестала работать после шага 4 | верните файл: `cp compose.yaml.bak compose.yaml`, `docker compose up -d` |
| `scp: No such file or directory` | проверьте имя файла (из вывода `backup.sh`) и папку |
| в итоге копии «нет файла-метки .doc-registry-copies» | по порядку: проверьте, что диск подключен (`ls` папки); если подключили после запуска контейнеров, `docker compose restart backup`; только если папка новая и диск на месте, создайте метку (шаг 15) |
| «Папка ... недоступна боту» | папки нет в `.env`: шаг 15, `BACKUP_DIR_2` и `docker compose up -d` |
| «контейнер копий не ответил» | `docker compose ps`: строки `backup` нет или она не `running`, выполните `docker compose up -d` |
| `update.sh` пишет «в .env ошибка» про `BACKUP_DIR_…` | путь папки копий начинается с `/` или `./`, не корень диска и не системная папка |
